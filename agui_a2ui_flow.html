Reference diagram · AG-UI / A2UI / ADK

How an ADK agent talks to a web frontend

The full lifecycle from one-time developer setup through a single user turn — event wiring, the A2UI catalog handshake, JSON generation, schema validation, and native client rendering.

Setup — you, the developer
Server — ADK agent runtime
Transport — AG-UI / A2A wire
Client — frontend renderer
Branch / loop path
Phase 0

One-time setup

Developer · happens once

Before any user ever connects. This is code you write once in agent.py; the ADK agent itself is not restructured — AG-UI and A2UI are layered around it.

1
setup

Build the ADK agent as normal

root_agent, tools, and any sub_agents / SequentialAgent / ParallelAgent topology — unchanged by anything below.

2
setup

Wrap it for AG-UI

An adapter intercepts ADK's native execution and translates it into AG-UI events — no change to the agent's internal logic.

from ag_ui_adk import ADKAgent, add_adk_fastapi_endpoint adk_agent_wrapper = ADKAgent(adk_agent=root_agent, user_id="demo_user") add_adk_fastapi_endpoint(app, adk_agent_wrapper, path="/")
3
setup — optional, A2UI only

Define or choose a component catalog

A JSON Schema listing exactly which components (Card, Row, Column, Button…) the agent is allowed to reference. Use the starter BasicCatalog, or your own schema mapped to your real design system for production.

4
setup — optional, A2UI only

Generate the system prompt from the catalog

The schema manager turns the catalog schema plus few-shot examples into an instruction string, and that string becomes the agent's normal system prompt.

schema_manager = A2uiSchemaManager(catalogs=[BasicCatalog.get_config()]) instruction = schema_manager.generate_system_prompt(role_description="...") root_agent = Agent(model="gemini-2.5-flash", instruction=instruction, tools=[...])
Phase 1

Session bootstrap — the catalog handshake

Client → agent · once per connection

Runs before the first message. The client declares what it's capable of rendering; the agent only ever gets to pick from that declared set.

1
client

Client announces supported catalogs

The frontend has its own catalog + renderer registered (its design system). It advertises this as supportedCatalogIds so the agent knows what it's allowed to speak.

2
orchestrator, if remote sub-agents exist

Orchestrator aggregates sub-agent catalogs

If this agent delegates to remote A2A agents, it collects their supported catalog IDs from each Agent Card and re-advertises the union upward in its own Agent Card.

Phase 2

A user turn begins

Client → transport → server

Fires every time the user sends a message — including messages that are really UI interactions (a button click) coming back from a previous turn.

1
client

User sends a message

Typed text, or a structured event from a previously rendered A2UI component (e.g. a button's action firing).

2
transport

Client POSTs RunAgentInput

One HTTP request carries everything the agent needs for this run.

RunAgentInput { threadId, runId, messages: [...], state: {...}, // shared app state context: [...], // semantic prompt items tools: [...], // frontend tools the agent may call forwardedProps: {...} // free-form extra data — must be read explicitly }
3
server

Middleware maps thread → session and invokes the agent

AG-UI's client-facing thread_id is mapped internally to ADK's own session_id — transparent to the frontend. Session state is primed, then agent.run() starts, same as any local adk run.

Phase 3

Agent reasoning and UI generation

Server · the ADK reasoning loop

Control flow is identical to a plain-text agent — nothing here rewrites SequentialAgent / ParallelAgent / LoopAgent composition. What changes is what the model is allowed to emit as output.

1
server

LLM reasons against its system prompt

If A2UI was configured in Phase 0, the catalog schema and few-shot examples are already sitting in this same prompt.

2
server

Local tool calls execute as usual

Standard ADK tool execution — arguments in, result back into context. No AG-UI-specific change to this mechanic.

↳ optional branch

Remote A2A delegation. If the task needs a sub-agent outside this process, the orchestrator calls it over A2A using its discovered Agent Card. That remote agent may itself be A2UI-aware and return its own createSurface / updateComponents JSON — which travels back through this same orchestrator as opaque cargo, regardless of which agent authored it.

3
server — A2UI only

Model emits three ordered JSON messages

Structure and data are kept separate on purpose, so structure can stream in before values are known.

1. createSurface { surfaceId, catalogId } — must come first 2. updateComponents { component tree, by name } — the schema 3. updateDataModel { values via JSON Pointer } — populates it
4
server

Validator checks the output against the A2UI schema

Runs before anything is streamed to the client — catches a malformed or out-of-catalog component reference at the source.

↻

Self-correction loop. If validation fails, a structured error — code: "VALIDATION_FAILED", surfaceId — is fed back to the LLM as a follow-up prompt, and it regenerates. This repeats until the JSON validates, then execution continues to Phase 4.

Phase 4

Event translation and the wire

Transport · AG-UI event stream

Everything the agent did in Phase 3 — text, tool calls, validated UI JSON — gets narrated to the client as a single ordered stream of typed events.

1
transport

ADK execution is translated into AG-UI events

RUN_STARTED TEXT_MESSAGE_START / CONTENT / END — plain text, token by token TOOL_CALL_START / ARGS / END — tool invocations STATE_SNAPSHOT / STATE_DELTA — shared state, JSON Patch (RFC 6902) (validated A2UI surface messages ride inside this same stream) RUN_FINISHED or RUN_ERROR
2
transport

Streamed to the client

One JSON event per line over Server-Sent Events by default (WebSockets also permitted). Events sharing a messageId or toolCallId must follow START → CONTENT/ARGS → END order, and the whole run is bracketed by RUN_STARTED / RUN_FINISHED.

Phase 5

Client reception and native rendering

Client · the frontend

The client already agreed to a catalog in Phase 1 — everything here is just resolving that promise into real components, never executing anything the agent sent.

1
client

SDK parses the stream and dispatches by event type

Text events feed the chat bubble. Tool call events either render through a developer-registered component (Tier-1 tool rendering) or, for A2UI, are handed to the surface renderer below.

2
client — A2UI only

Renderer resolves the surface

createSurface → look up catalogId in the client's registered catalog + component map updateComponents → build/patch the flat component tree by id reference updateDataModel → bind values into the tree, re-render — no iframe, native components
3
client

State deltas patch the shared store

STATE_DELTA is applied as a JSON Patch to local state, which re-renders any bound UI immediately.

↺

The loop closes here. Updated client state — and any user interaction with a rendered A2UI component — becomes part of the next RunAgentInput, back at Phase 2. This is what makes AG-UI bidirectional by default rather than a one-way broadcast.

Reflects the AG-UI / A2UI / ADK integration surface as documented in mid-2026 (A2UI v0.9–v1.0 candidate). Both protocols are moving quickly — verify exact event and field names against current docs before shipping.
